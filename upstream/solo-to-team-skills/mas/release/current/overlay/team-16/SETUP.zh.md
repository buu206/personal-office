# 把 16 席团队带到自己的平台

[返回建队台](index.html) · [English](SETUP.en.md) · [本轮16席验证范围与限制](VERIFICATION.zh.md)

这份模板包含 **16 席、6 群、26 条建议群籍**。第一单可以只启用首席、生产、审核三席；其余岗位按任务启用，完整模板仍可编辑和导出。

先在建队台核对岗位职责、群成员和“交接”，点“保存配置文件”。这个 JSON 是你以后继续编辑的底稿。职责和群说明保留原有缩进与换行。 删去岗位后，检查提醒中列出的现行职责和群说明；成员名单会同步调整，正文仍由你核对和修改。提醒只指出文字里出现的未选岗位名，不会代你改派或判断实际授权。再在页面下方选平台下载；保存文件本身不会创建账号、建席、派工或开通工具权限。

## OpenMausBot

1. 在建队台选 OpenMausBot。需要六群时逐群勾选，默认应答方式是“仅提及时应答”。不勾选就只建席位。
2. 下载部门 JSON。在 OpenMausBot 的新建或分享入口进入“模板”，点“导入”，选择文件。先看预览是否为你要的席位和群；确认无同名冲突后添加。
3. **分别核对 Bot 默认、当前对话和新委派子会话。** 本次 0.1.148 原生导入后仍出现“完全访问”，文件中的 `ask` 不是实际权限证明。到该席的“资料 → 权限 → 批准层级”核对默认设置，再读回实际对话。这个资料面板改为 Ask 不会自动收窄已显式设为 Full 的旧对话；聊天栏的 Ask 只改当前对话。新委派以接收 Bot 的默认层级为起点，不能用首席原对话 Ask 代替检查。若与本单要求不符，先停止该轮并核清。
4. 在建队台下载“群规全文”，向对应助手提供适用小节，请它回读职责、委托方和回件对象。JSON 已含执行摘要；全文不会自行加载。你改过的团队配置优先，默认全文只作参考。
5. 首单前核对允许使用的目录、材料和回件渠道。本地链接或“保存副本”按钮出现不等于可下载，需实际点开核对。机务处群内只用约定文件代号或相对名，敏感定位信息按已批准的渠道提供。核实实际执行席、独立审核席与回件，按实际记录判断是否接通。

最新候选 B 已经原生导入并回导核对：16 席岗位正文、六群公告与设置、26 条成员关系一致。同名席被宿主加后缀，群 ID 重建；头像会由宿主转换，审批字段不随回导保留。已做的生活官、顾问团、合成情报专属链及受限实施与独核专项见本轮验证说明。后一次任务的两份群附件下载核验通过，但群派单披露内部路径、首席原对话首个文件保存入口失败，不能称全部通过，也不代表每席全部业务均已跑通。

首次督查轮因新子会话显示“完全访问”而被操作员停止，原期限内未完成。随后，此次测试部门 16 岗的 Bot 默认逐一改为 Ask 并原生读回；新一轮固定群外督查在自己的新期限内完成了受限合成文字核查。新子会话的本人接单与 Ask 由操作员在原生界面观察，未手改该新线程权限，不能写成首席自行验证。另已核对 16 个可见既有直接对话为 Ask，历史工作对话尚未全量核对，不推广为所有对话均已设置正确。

点对点派单要核对当前通道的长度上限：本次 0.1.148 为每条 4000 字符。交棒包保留一份完整素材、成品要求与登记，去掉重复转述；无法完整送入就报告具体限制，不截断关键材料，也不把已发送或排队当成已接。送达和回传路径须分别核对：一次合成试验中，创意官直接交给生产官、生产官直接交审，但审核结果沿原委派逐层返回；不能写成审核官直接送达首席。需要特定直接报告通道时，应先验证该通道。

## DeepSeek Harness

1. 在建队台选 DeepSeek Harness，保留“原生项目”，下载 ZIP。
2. 解压到新空目录。选择包含 `team.definition.json` 的那一层作为工作区，保留以点开头的 `.dsh` 文件夹。
3. 开一个新会话，使用 `/solo-to-team`，先让它核对 16 席及本单分工。群名册是协作说明，不会生成原生聊天室。
4. 群规在 `references/template-rules/`。让负责席读适用小节；根会话承担派工和交回，具体生产与独审交给不同席。不能只凭配置文件存在就认定已派工。
5. 给一份小型、可核对的任务，检查实际子任务、成品及审核记录，再扩到自己的正式材料。

“DS Bot 建队计划”是另一个可选入口，不是 DeepSeek Harness 原生项目。它依据指定版本源码制作，尚无真实 DS Bot 建队验收；请按各自入口说明使用。

## WorkBuddy

1. 下载 WorkBuddy ZIP，在“我的专家 → 创建专家团”附上文件，请内置创建器**私有导入**；先检查名称与既有专家是否冲突。
2. 核对实际创建结果。完整模板有 16 席；此前三席首单包的测试结果不等于平台最多只支持三席，也不保证当前账号能一次创建或并发运行全部席位。
3. 第一单可先用首席、生产、审核三席。根/主理人的传输限制不改变专属主管关系：中转必须保留原委托方、原授权和原回件对象。
4. 全文规则位于团队目录中的 `references/template-rules/`。每席岗位卡也给出路径。要求助手回读适用内容；不能把文件随包当作已读取。
5. 对需要私密咨询或直接报告用户的任务，先核实宿主是否确有合适通道。不能支持时只说明能力缺口，不把私密结果交给中转主理人。

## Grok Bot

新 Bot 首次启动可能直接向用户问候，建席后须查看真实消息路由，再用无敏感内容的小题核对已接与回件对象。一次样本的执行方依据平台会话记录回报：该席自动收到了共享用户上下文；自定义岗位描述不构成隔离。传入描述的指纹核对不等于已保存人设全文已读回。若任务要求严格隔离，在创建或首次启动该任务 Bot 前，先核实宿主是否支持且所需隔离是否已生效；未核清前不要交入须隔离的材料。只核共享上下文是否注入及其范围，不索取或转发其正文。

1. 选择 Grok Bot，填写本次批次标记并下载引导 ZIP。续办同一批次沿用原标记。
2. 打开 ZIP 中的 `Start-here.html`，在自己的主 Bot 对话附上 `grok-plan.json`，复制页内预览请求。核对实际缺席、已有席和绑定，再处理缺项。
3. 如果当前账号不能代建，使用侧栏“＋ → Create a Bot”逐个补建；向每个 Bot 提供它在 `roles/` 下的岗位卡及适用的群规全文小节，请它回读。
4. 群关系是逻辑协作说明。手动派工、搬文件或转交结果时如实标为人工，不把引导包称为已验证的一键原生导入。

## 第一单怎样算接上了

实际执行席拿到正确版本的材料并交出可打开的成品；另一审核席打开同一成品核对；有问题退回本单原执行席；原会话收到修订后的成品和审核结论。岗位数量、导出成功、界面显示“完成”，各自只能证明对应的一步。
