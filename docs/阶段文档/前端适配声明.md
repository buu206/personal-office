# 前端适配声明

日期：2026-11-18。阶段3-0已确认并进入3-1。用户新增“机器人办公室”设计要求，本版替代此前“不做视觉重设计”的方案；本机采用、无真实模型调用、无云上线的边界不变。

## 1. 项目判断

主要用户为当前用户，桌面浏览器优先，兼顾窄窗口。新的主屏是有3D视觉效果的机器人工作场景，机器人与实际团队角色对应。左侧项目进度与数据，中间办公场景和白板/电视进度屏，右侧任务输入。

用户明确允许虚拟模式进度。Demo中的角色工作、消息、进度和成果均为模拟，必须持续显示“模拟演示”，不表示模型或Agent已实际执行。真实执行平台与业务任务仍另定。

当前交付视觉稿并明确Demo路线；下一代码阶段先做代表页面，用户反馈后继续细化。既有三个离线工具保留可用，逐步统一壳层、配色和控件，不删除已验收功能。

## 2. 输入资料与视觉方向

已读PRD、技术适配声明、决策台账、阶段2-1证据及前端手册全文。新增输入是用户本轮提供的机器人图片及口述布局。

机器人共有特征：圆润白色光泽外壳、黑色屏幕脸、粉色像素眼睛与表情、青色胸灯、黑色关节。不同角色靠配饰、工位与可读角色名区分，避免只靠颜色。

三版完整视觉稿保存在`docs/设计参考/机器人办公室/`：

| 方向 | 实际画面 | 取舍 |
| --- | --- | --- |
| A 奶油白独立工位 | 日光、白粉色室内、分区工作桌 | 办公生活感更强，适合想保留独立工位的场景 |
| B 石墨灰指挥工作室 | 深灰侧栏、暖光室内、后墙电视 | 沉浸感更强，整体偏深色 |
| C 浅灰粉环形协作桌（推荐） | 环形桌、集中角色、后方白板 | 角色和进度更容易看清，适合第一版交互Demo |

五个机器人只是视觉稿的示例人数，不固定最终团队为五人。实际展示要与选用团队一致：大团队按房间/分页分组，展示当前房间人数和团队总数，每个角色可到达，不能默默省略。具体分组实现随选定视觉确定。

视觉稿文字和百分比是概念占位；局部文字不准确、数值口径不统一，不能作为最终文案或验收证据。Demo将用HTML文字与同一状态源渲染真实可操作的输入框、数据和进度屏。

## 3. 技术选择与维护边界

推荐先做2.5D交互Demo：预渲染的立体场景/角色素材，加HTML布局、点击热区与轻量动画。可实现角色选择、任务输入、进度变化与工作状态展示；不先引入自由旋转镜头、3D建模和复杂引擎。若用户需要这些能力，再调整技术方案与资源成本。

- 保留原生HTML/CSS/JavaScript和现有Node构建能力；本轮未新增框架或运行依赖。
- 新工作台代码将放在本产品`frontend/`，与`upstream/`原始快照分开。素材选定后存到项目内，不依赖外部生成路径。
- 现有团队编辑、素材打包和更新工具保持现有入口。统一外观时在产品侧维护明确补丁与构建过程，不覆盖来源清单、不只改生成HTML。
- 服务仍绑定127.0.0.1；不公开到局域网或公网，不调用真实模型、不安装宿主、不发送消息。
- 生成视觉稿使用内置图像工具，不是产品运行时接入图像API。

## 4. 模拟状态与数据契约

新工作台使用一个明确标记的模拟项目状态源，左侧数据、机器人状态、右侧消息、中央白板均由同一状态驱动，不能各自播放无关动画。

| 状态 | 用户体验与行为 |
| --- | --- |
| 未开始 | 可以输入任务、查看角色，演示标识可见 |
| 演示中 | 角色按预定顺序进入研究、撰写、设计、审核；进度和消息同步 |
| 暂停 | 角色与进度暂停，可继续；不声称停止真实后台任务 |
| 待用户确认 | 明确当前候选及继续后的模拟变化 |
| 演示完成 | 标明演示完成，展示模拟结果与重新开始入口 |
| 输入错误/恢复失败 | 给出可理解原因，保留可恢复输入；不静默重置项目 |
| 重载恢复 | 恢复本地已保存项目、角色与演示进度；默认暂停，避免跳进度 |

计划使用带版本与结构校验的本地持久化状态，并提供导出/导入。具体存储及失败处理在阶段3-1开发文档冻结；不能仅用内存保存重要状态。不保存账号凭证，日志不记录完整用户任务正文。没有后端任务ID、队列或真实模型结果。

既有工具文件契约不变：团队JSON沿用`solo-to-team.definition` 1.0.0与共享校验器；ZIP保留原始素材、清单和任务条件；更新器通过三版本和人工选择另存，不覆盖原文件。

## 8. 2026-11-18视觉定稿与本阶段实现

以B的深色工作室结合围桌布局，弃用粉色；主色深海蓝、交互科技蓝、灯光暖琥珀色。默认演示团队为5个不同轮廓的角色，保留切换完整16席团队及分页入口，人数和名称由当前团队数据决定。生成的透明角色图提供5种视觉家族，额外成员以编号与角色名持续区分；本阶段不声称已为16席分别建模。

产品侧用原生HTML/CSS/JS实现，房间背景与透明角色分层。浏览器localStorage保存版本化状态，配置JSON导入导出辅助备份；重载时恢复为暂停。已有上游三页保持原样并提供入口，样式统一留3-2。

会议室代表页采用中央长桌，两侧角色朝向桌面，坐姿与站姿混排。后墙进度屏随模拟项目变化。待机时各席偶尔微倾，运行时统筹与当前环节的角色切换工作节奏。系统开启减少动态效果时，座位保持静止。

会议室布局暂定。外围界面使用青蓝数据线、暖黄当前节点、等宽命令输入和 JSON 状态输出。项目比例显示总进度，节点输出显示环节内进度。点选节点、选中对应机器人与查看状态构成同一条交互链路。


本次视觉修订为宝可梦草地工作营。背景为草坪、白云、树与围栏，皮卡丘统筹、妙蛙种子研究、杰尼龟撰写、梦幻创意、喷火龙审核。梦幻有独立悬浮动作。主屏主题维护于 frontend/pokemon.css，任务与存档仍由现有状态模块处理。新版以伙伴状态卡展示节点信息，素材来源见 docs/设计参考/宝可梦营地.md。


本次角色修订使用本地 Three.js 0.170.0 进行实时 WebGL 渲染。五种模型在 frontend/creatures.mjs 中由立体网格及关节组合构建，属于圆润简化造型。角色支持分段行走、转向、眨眼、四肢与尾部动作，飞行角色独立盘旋。草地上设定了错开的漫游区域，中央树桩区域留空。职位标签跟随投影，点模型或标签查看职责并触发短暂回应。原有静态角色仅作为 WebGL 不可用时的回退，界面会明确提示。减少动态效果设置会停用动作。Three.js 与许可证保存在 frontend/vendor，运行时无需请求 CDN。


最新代表页使用已确认的2D像素角色（frontend/pixel-camp.mjs），按实际速度选择八方向行走帧。人物卡以职位为主标题，包含角色立绘、属性、工作分工、当前任务进度与状态，点击卡片选中场景角色。属性对应所展示的宝可梦，任务进度来自现有模拟状态。16席团队按原有分页展示，本页每次最多五张卡。界面由 frontend/trainer.css 维护，使用红色委托图鉴、金边属性卡和训练师对话框。完整团队可能复用角色形象，职位及职责来自实际团队配置。
